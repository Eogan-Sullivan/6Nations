## Design specificity verdict

The product feels authored for fantasy rugby rather than a generic dashboard. The emerald/amber stadium palette, Chivo/Inter pairing, pitch editor, captaincy badges, nation quota, and freshness language create a clear identity. The main missed opportunity is not visual distinctiveness; it is making that identity carry the full product contract consistently across matches, stats, leagues, and every data state.

The deterministic detector returned no findings. That is a useful clean signal, but it does not cover the mobile layout, state completeness, or interaction conflicts found in source review.

## What is working

- The squad editor has a strong product-specific core: pitch/list alternative, active-slot guidance, budget and nation counters, explicit captain/vice-captain controls, reserve ordering, and validation.
- The visual system is coherent across themes: tokens, Chivo headings, Inter body text, tabular numbers, emerald actions, amber deadline/captain cues, and clearly differentiated freshness states.
- The copy is unusually honest for a demo: synthetic data, no official affiliation, no real submission, and “unknown stays unknown” are all trust-building choices.

## Priority issues

### [P1] Mobile has two competing fixed action systems

`SquadScreen.tsx:703-719` renders a fixed mobile “LOCK SQUAD” bar while `CommandDock.tsx:46-114` renders an expandable fixed navigation dock over the same bottom region. The dock is rendered after the action bar and can cover it when expanded; the scroll padding also only reserves a generic 116px. This makes the primary task intermittently inaccessible and creates a confusing hierarchy.

Fix by giving the squad action bar and nav a single coordinated bottom-surface model: either fold navigation into the action bar, or reserve measured dock height and keep the lock action above it.

### [P1] Bench controls are not mobile-safe

`SquadScreen.tsx:457-491` keeps three reserve cards in one row, and each card contains two arrow buttons plus “Swap with starter”. At narrow widths those controls cannot fit comfortably inside each `reserveItem` (`:1371-1374`). This is a predictable 390px failure even though the overall page is intended to be responsive.

Stack each reserve as a full-width row on narrow screens, or move reorder/swap into a single “Reserve actions” sheet with clear priority controls.

### [P1] The screen state model is far behind the product requirement

`AppScreen.tsx:12-23` exposes a freshness banner, but Matches, Leagues, Stats, and Profile are largely hard-coded demo surfaces. They do not demonstrate complete loading, empty, error, offline, stale, incomplete, provisional, official, and corrected states as required by `Plan.md`. The result looks polished in the happy path but does not teach users how trustworthy each screen is.

Create a shared state-story component and implement each required state on every data screen before calling the experience complete. Keep the status copy precise: “Halftime update”, “Mid-match snapshot”, and “Sunday update”.

### [P1] Custom squad modals do not share the accessible overlay behavior

`OverlaySurface.tsx:18-29` focuses the close control and restores focus, but the squad-specific modals in `SquadScreen.tsx:721-1042` only set `accessibilityViewIsModal`. They lack the shared focus entry/return behavior, and several close paths are custom. Keyboard and screen-reader users can lose their place after opening player details, review, or reset flows.

Route all overlays through one primitive or extract the focus-management behavior into a hook, then test Tab/Escape/focus return for each modal.

### [P2] Information architecture labels are inconsistent with the product contract

The specified primary tabs are “My Squad · Match Centre · Leagues · Stats & Fixtures · Profile”, while `CommandDock.tsx:13-18` exposes “Squad · Matches · Leagues · Stats · Profile”. This is small visually but meaningful in onboarding, deep links, accessibility announcements, and product language.

Use the product names consistently, especially “My Squad”, “Match Centre”, and “Stats & Fixtures”.

### [P2] The design system has implementation drift and no durable design artifact

The repository has no `PRODUCT.md`/`DESIGN.md` and the documented design files referenced by `frontend/README.md:110-112` are absent. `frontend/tailwind.config.js` also defines a second palette that differs from `theme/tokens.ts`. Even if Tailwind is lightly used today, this creates a future fork in colors, radii, and typography.

Choose `theme/tokens.ts` as the source of truth, remove or reconcile the duplicate palette, and document the incumbent system before the next feature slice.

## Persona red flags

- **Jordan, first-timer:** The first task asks the user to understand a pitch, slot selection, captaincy, reserve ordering, filters, and a separate bottom navigation model. “Select a jersey to fill that position” helps, but the first successful path still has too many simultaneous controls. Add a short three-step orientation and keep one primary next action visible.
- **Alex, power user:** The squad editor has useful filters and a list view, but no keyboard shortcuts, no compact bulk workflow, and repeated modal transitions for player detail/review. The power path should keep selection, captaincy, and review reachable without losing scroll position.
- **Morgan, screen-reader/large-text user:** The shared overlay has good intent, but squad-specific overlays do not restore focus. Dense 9–12px labels, uppercase letter spacing, and the three-column bench controls will degrade quickly at 200% text scaling.

## Minor observations

- The mobile dock hides all destinations until expanded, so navigation is not discoverable at first glance.
- Some labels are overly compressed (“PROVISIONAL”, “ROUND 01 · SYNTHETIC”, “PRICE / CREDITS”); sentence case would improve scanability without losing the sports-broadcast tone.
- The web export bundles approximately 2MB of JavaScript plus a broad icon-font set; consider loading less icon/font surface for the first route.
- The UI has strong empty/error copy on the squad screen but less consistent recovery affordance on Matches, Stats, Leagues, and Profile.

## Questions to consider

- Should the squad lock action remain persistently visible on mobile, or should navigation collapse into a single task bar while editing?
- Is the “command centre” navigation meant to be a brand signature, or should it behave like conventional persistent tabs for faster discovery?
- Which matters first for the next pass: mobile task completion, full data-state storytelling, or accessibility hardening?
