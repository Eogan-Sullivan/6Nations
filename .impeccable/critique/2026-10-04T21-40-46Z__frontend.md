## Design Specificity Verdict

The interface is authored for Six Nations fantasy rugby rather than category-interchangeable: the emerald pitch, jersey-first roster, nation quotas, captaincy signals, freshness language and matchday command dock create a clear point of view. The strongest opportunity is to make that specificity carry more of the workflow so the page feels less like a long admin form beneath the pitch.

Browser overlay: unavailable because no browser automation tool was exposed in this session. The existing Playwright suite was run instead.

## Overall Impression

The visual system is confident and coherent, especially on the squad surface. It currently over-explains the product in parallel: deadline, HUD, validation, local status, pitch, bench controls, quotas, player selection, rules and fixed actions all compete for attention. The single biggest opportunity is to make “select → validate → lock” the dominant journey and demote everything else until it is needed.

## What's Working

- The pitch and jerseys are a credible visual hero; the product is immediately legible as fantasy rugby.
- Data confidence is treated as product UI, not fine print: provisional, demo, incomplete and reconciliation states are surfaced consistently.
- The interaction model has good recovery intent: list mode, search/filtering, modal dismissal, failed storage messaging and reduced-motion handling are all present.

## Priority Issues

### [P0] Visible heading and accessible heading disagree

`SquadScreen.tsx:301-303` renders visible text “My Squad” but overrides the accessible name with “Your squad. Your call.” The current Playwright run fails all 8 tests at setup because `getByRole('heading', { name: 'My Squad' })` cannot find the heading. This is a real screen-reader mismatch, not just a brittle test.

Fix: remove the custom `accessibilityLabel`, or make it equal to the visible heading and move the motivational copy into the description. Re-run the suite before any visual polish.

Suggested command: `$impeccable audit frontend`

### [P1] Squad composition is too dense for the primary task

The squad page presents deadline, three metrics, validation, pitch/list toggle, 18 slots, reserve reorder/swap controls, nation distribution, status, review/reset actions, a full player pool, two filter groups, search, and rules in one continuous decision surface. The “player pool” is the actual next action, but it starts after a very large amount of setup and status.

Fix: keep deadline + compact progress + pitch above the fold; collapse nation distribution and explanatory scoring into “Tactical Desk”; keep reserve actions behind the selected reserve; make the player pool sticky or jump to it after a slot is selected.

Suggested command: `$impeccable distill frontend`

### [P1] Mobile has two fixed bottom layers with competing primary actions

`SquadScreen.tsx:711-719` adds a fixed mobile “LOCK SQUAD” bar while `CommandDock` adds fixed bottom navigation. The source compensates with padding, but the two layers create a tall persistent obstruction and make “lock” visually compete with navigation even when the squad is incomplete.

Fix: use one bottom action surface: keep navigation collapsed and elevate a contextual squad action above it only when the draft is valid; otherwise show “Review squad” or “Fix 3 checks” rather than a disabled/early lock affordance. Validate at 320–390px with keyboard open.

Suggested command: `$impeccable adapt frontend`

### [P2] Copy and IA drift reduce polish

The reserve empty state renders “Open cover cover”, and the Tournament Hub says “Match Center” while the primary nav says “Match Centre”. “Rules & Admin” is presented as a destination but has no route. These details make the product feel unfinished and create false affordances.

Fix: centralize navigation labels/routes, remove the duplicate “cover”, and either implement the rules destination or label it as informational/non-navigable.

Suggested command: `$impeccable clarify frontend`

### [P2] Modal patterns are split between shared and bespoke implementations

Matches/leagues use `OverlaySurface`, while squad uses several bespoke `Modal` trees. That makes focus return, close affordances, sheet sizing, and heading semantics harder to keep consistent. The player detail and review modals do not share the same header/close treatment as the rest of the app.

Fix: route squad overlays through the shared surface primitive where possible, or extract one squad-specific variant with identical focus trapping, close behavior, max-height and mobile sheet rules.

Suggested command: `$impeccable polish frontend`

## Persona Red Flags

- **Jordan (first-timer):** lands on a wall of rugby terminology and 18 empty slots before understanding the next concrete action. The current “Select a jersey…” cue helps, but the pool’s position below the pitch requires extra scrolling on mobile.
- **Alex (power user):** can use list mode and filters, but must still traverse captaincy, reserve ordering and review controls manually. There is no fast path for keyboard users or a compact “complete the remaining slots” mode.
- **Sam (screen-reader/keyboard user):** encounters a heading named differently from its visible text, and the current test failure shows this is already breaking role-based navigation. The modal patterns also vary across screens.

## Minor Observations

- `CommandDock` renders a desktop navigation toggle that is always disabled while its label says “Collapse/Expand navigation”; remove the disabled control or make desktop collapse real.
- `AppScreen` gives secondary data-confidence copy a prominent full-width band on every destination; reserve the strongest treatment for stale/error/provisional states.
- The `Button` selected state uses the full text color as a background, which is high-contrast but visually heavier than the rest of the system; use the active surface for filters and reserve filled emerald for primary actions.
- The route inventory and implementation are ahead of the tests in some places; update test semantics after fixing the heading rather than weakening selectors.

## Questions to Consider

- What should the user see in the first 10 seconds: the pitch, the next slot to fill, or the deadline?
- Can “Tactical Desk” own every secondary rule and audit detail so the squad page reads like a game board?
- Should “LOCK SQUAD” exist before the squad is valid, or should the primary action always express the next fix?
